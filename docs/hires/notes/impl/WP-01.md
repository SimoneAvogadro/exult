## 2. `test_ibuf_golden` and `ibuf_golden.txt`

**Stream** (`ibuf_ops.{h,cc}`, shared with WP-04's O1 test):
* The PRNG is SplitMix64, never `std::rand()` or `<random>` distributions, so the digests are the same on every platform (G6, Windows).
* `make_ibuf_op()` draws an op from the generator state and the logical geometry only, never from buffer contents. One stream can therefore drive buffers of any pixel scale.
* All 28 op kinds are covered: `set_clip`/`clear_clip`, `fill8` (whole and rect), `fill_hline8`, `draw_line8` (with and without xform), `copy8`, `copy_hline8`, `copy_hline_translucent8`, `fill_hline_translucent8`, `fill_translucent8`, `copy_transparent8`, `get_pixel8`, `put_pixel8`, `copy`, `get`, `put`, `fill_static`, `paint_rle` (through `Shape_frame` and direct), `paint_rle_remapped`, `paint_rle_translucent`, `paint_rle_transformed`, `paint_rle_outline`, the flat `Shape_frame::paint`, `draw_box`, `draw_beveled_box`, `create_another` and `is_visible`.
* The fixtures are synthetic:
  * 17 translucency tables, built like `Palette::create_trans_table` (blend with a colour, then the nearest entry of a synthetic ramp palette);
  * 4 remap tables;
  * 24 RLE frames built with `Shape_frame(pixels, …)`, 1-64 px wide (encode_rle's `runs[200]`, P6, is out of reach), mixing transparent, repeat and literal runs, with 30 % translucent indices;
  * 4 flats;
  * source pools for the copies.
* Upstream's scale-1 contract (TB-12):
  * clip rectangles always overlap the buffer. An empty or outside clip makes upstream `draw_line8` write outside the buffer, which was found while designing the stream;
  * `copy()` rectangles lie inside the buffer;
  * `get_pixel8` reads inside the buffer.
* `Ibuf_geometry` carries `offset_x/offset_y` (default 0). Coordinates are drawn relative to the logical extent `[-offset, size-offset)` and the PRNG is used the same way, so WP-04 can drive views with negative offsets **without changing the golden stream**. This was verified: after the refactor the re-recorded digests equal the file.

**Buffers per block.**
* Block 0: owned, 320x200.
* Block 1: a layer-constructor buffer, 355x200, 4 px guard band, pitch 364.
* Blocks 2 and 3: 37x1 owned, and 1x29 as a layer with guard 2 and pitch padding 3.
* Blocks 4-19: owned and layer buffers in turn, with random sizes (8-400 × 8-300), guard bands of 0-6 and pitch padding of 0-12.
* Blocks 20-23 (golden v2, added after the review): layer buffers with a **logical offset**, the state of the engine's
  main buffer when the full area is larger than the game area. A test-only subclass `Offset_buffer8` sets
  `offset_x/offset_y`, moves `bits` by `offset_x + offset_y·line_width` and calls `clear_clip()`, as
  `Image_window::create_surface` does, and the generator gets the offsets through `Ibuf_geometry`:
  * block 20: 355x200, `offset_x = 17` (a 320x200 game area), guard 4, pad 1;
  * block 21: 320x240, `offset_y = 20`, guard 4;
  * block 22: 401x263, offsets (40, 31), guard 2, pad 5;
  * block 23: random; it came out 148x39 with offsets (119, 29), guard 1, pad 2, so most of the logical extent is negative.

  They pin upstream's offset paths: `fill8(pix)` from `bits - offset_y·line_width - offset_x`, `fill_static`'s
  `(y - offset_y)` rows, `clear_clip`/`set_clip` with offsets, and every op at negative logical coordinates. Each
  block has its own generator, so blocks 0-19 kept their v1 digests.
* Each block also has an owned second buffer (1-48 px) for `get` and `put`.
* All memory starts with random bytes, so nothing reads uninitialised memory.

**Digest.** FNV-1a-64 over:
* the block number;
* the target's **whole allocation**: for layer buffers that includes the guard band and the pitch padding, so upstream's `fill8(pix)` writes into the guard band are pinned too;
* the second buffer;
* a hash of everything read back (`get_pixel8`, `is_visible`, `create_another` contents through `get_pixel8`);
* both clip rectangles.

**`fill_static`.** It draws from `std::rand()`, whose sequence differs between glibc, MSVCRT and UCRT. It
therefore cannot enter a cross-platform digest. Each `fill_static` op does this:
1. `std::srand(seed)`, then the call;
2. a comparison of the whole allocation with a model of upstream's loop: one `rand() % 5` per logical pixel, row-major, 0-1 → black, 2-3 → gray, 4 → white, nothing else touched;
3. the memory is restored.

`fill_static_mismatches == 0` is checked. This pins upstream's behaviour on every platform. WP-04's O1 test
checks "RNG parity" separately.

## 3. `rle_writer.h`

`Rle_writer` emits Exult RLE frame data:
* raw and encoded scans of any length up to the format's 15-bit limit (32,767 px), positions within s16;
* `raster()` turns a pixel raster with a transparent index into raw, encoded or alternating scans, origin as in `encode_rle`;
* malformed data on demand: `begin_encoded(x, y, length)` followed by runs that need not add up to the length, and `bytes()` for garbage;
* it refuses what the format cannot express (`std::invalid_argument`), including an empty raw scan, whose header
  would be the u16 0 terminator (review fix); an empty encoded scan (header 1) is valid, and `bytes()` can still
  write an early terminator on purpose.

`decode_rle()` is the reference decoder:
* it never reads past the end of the data;
* `strict` rejects runs that pass the scan length;
* `clamp` cuts them at the scan length while the input still skips the whole run, and the scan ends there. These are the WP-04 semantics of §3.1 / MS-5.

`test_rle_writer.cc` (all at scale 1, as upstream's painter cannot take malformed data):
* 40 random rasters × 3 styles: decode == raster, and `Image_buffer8::paint_rle` equals decode + clip, with random clips and frames hanging off the buffer;
* `Shape_frame::encode_rle` output decodes to the same raster, which validates the decoder against the engine's encoder;
* scans of 5,000 and 4,500 px (raw and encoded) under three clips, and the 32,767 px maximum (encoded and raw);
* exact bytes of a malformed repeat run, strict vs clamp decoding, and a malformed literal run followed by a correctly read scan;
* an empty raw scan throws; an empty encoded scan is followed by a scan that the decoder and `paint_rle` both read;
* every prefix of a valid stream returns false in both modes. Under ASan this shows that the decoder never reads past the end.

## 4. `hires_present` skeleton

## 6. Build-list lint

`tools/hires/check_build_lists.py` (Python 3.8+, standard library only).

**What it collects.**
* Every `*_SOURCES` variable of every `Makefile.am`, with `$(VAR)` expansion and all conditional branches.
* Every object and header named in `Makefile.common`. Objects are mapped to their `.cc`, `.cpp`, `.c`, `.mm` or `.m` source.

**What it checks.** Each collected file must be in:
* `Exult.vcxproj` and `.filters`, parsed as XML (any `Include`);
* `ios/Exult.xcodeproj/project.pbxproj`. The script parses the OpenStep plist (the file starts with a BOM) and resolves each file reference's path through the group tree (`<group>` and `SOURCE_ROOT`). This is an exact path match, not a basename match.

Comparison ignores case.

**What it does not check.**
* Generated files: targets of makefile rules (with variable expansion), `BUILT_SOURCES`, and anything git ignores.
* Files that do not exist.
* New files that git does not know yet **are** checked.

**Companions** (review fix; `tools/hires/build_lists_companions.txt`). A pair `<first> <second>` means: wherever a
build description lists the first file, it must list the second one too. The lists are every variable and every
rule (prerequisites and recipe) of each `Makefile.am`, `Makefile.common` and `Makefile.mingw`, without expansion and
under the same conditionals or fewer (automake `if`, GNU make `ifeq`/`ifneq`/`ifdef`/`ifndef`, `else`); every
`*.vcxproj` and `*.vcxproj.filters` under `msvcstuff`; every native target of the Xcode project and its file
references. A source and its object match (`imagewin/ibuf8.cc` = `imagewin/ibuf8.o`). A pair is inactive until its
second file exists or is listed somewhere; with `--strict`, a pair whose first file is listed nowhere fails.
* Seeded with `imagewin/ibuf8.cc imagewin/ibuf8_scaled.cc` (§6.1), inactive until WP-04 creates the file. Then the
  lint requires `ibuf8_scaled` in the 14 lists that hold `ibuf8` today: `libimagewin_la_SOURCES` (inside
  `if HAVE_SDL`, so not only under `if BUILD_EXULT`), `IMAGEWIN_OBJS`, `IPACK_OBJS`, `EXULT_THUMB_OBJS`,
  `HIRES_UNIT_OBJS`, `Makefile.mingw`'s `ES_IMAGEWIN_OBJS` and its `u7shp`/`exult_shp` link rules,
  `Exult.vcxproj(.filters)`, `exult_studio.vcxproj(.filters)`, and the Xcode target `Exult` and file references.
* Check on the real tree: the probe pair `imagewin/ibuf8.cc imagewin/imagewin.cc` reports exactly the 9 of those
  lists without `imagewin.cc`; `imagewin/ibuf8.cc imagewin/imagebuf.cc` reports none.

**Options.**
* Allowlist: `<glob> <projects>  # reason`, where `**` crosses directories.
* `--companions FILE` (default: `build_lists_companions.txt` next to the script).
* `--strict` also fails on allowlist entries that match nothing and on companion pairs whose first file is listed nowhere.

## 7. `ci.sh`

Usage: `tools/hires/ci.sh [--lanes "o2 asan sdl32"] [--jobs N]`. `ROOT` defaults to the directory that holds the
source tree. It works through these steps:
1. The `uv` bootstrap of `requirements.txt` into `tools-venv`.
2. `autoreconf` if `configure` is missing.
3. Per lane:
   * configure with the §7.1 commands, only if there is no `config.status`;
   * `make -j6`; in `build-asan` under `ASAN_RUN` (`setarch -R`, `detect_leaks=0`, a timeout);
   * the lane assertions: `build-asan/tests/Makefile` has the setarch/timeout `TEST_WRAPPER`; `build-sdl32` resolves pkg-config 3.2.14 and its `SDL_CFLAGS` point at `prefix-3.2`;
   * `make check`. In `build-asan` it runs with `-j1`, so only one sanitizer process runs at a time.
4. The lint (`--strict`, under `timeout 600`).
5. pytest (`-p no:cacheprovider --basetemp=$ROOT/tmp/pytest-ci`).
6. With `U7_BG_STATIC` only: `make check-game` in `build-o2`, and in `build-asan` under `ASAN_RUN` (its `make all`
   runs the ASan tools of the data build) with `EXULT_WRAPPER`. Only lanes whose configure, make and lane check
   passed get this step; for the others it is logged and listed as skipped in the summary (review fix).

Other behaviour:
* Every step runs under `timeout` (inside `check_lane` and the bootstrap's import check too), and the output goes to `$ROOT/tmp/ci-<date>.log`. A one-line summary goes to stdout.
* A failed step runs once more. Fail-then-pass is reported as **FLAKY** (suspected hardware fault or intermittent bug) and gives exit status 3, never a silent pass.
* A `flock` on `tmp/ci.lock` prevents two runs at once.

Final run on the final tree: `ci.sh: 18 passed, 0 flaky, 0 failed` in 48 s with `U7_BG_STATIC` set
(`tmp/ci-20261005-002524.log`). The earlier runs `tmp/ci-20261005-001655.log` and `…-002112.log` gave the same
result. After the review fixes: `ci.sh: 18 passed, 0 flaky, 0 failed` in 49 s (`tmp/ci-20261005-011434.log`). A

## 9. Deviations from the spec

1. **`fill_static` is checked against a model, not hashed** (§2). Its output depends on the C library's `rand()`, and a hashed digest would break G6 on Windows. The model pins the same upstream behaviour.
2. **Additional test files** not listed in §6.1's layout:
   * `unit/ibuf_ops.{h,cc}`: the op stream, shared with WP-04 and offset-aware;
   * `unit/test_support.h`;
   * `unit/test_rle_writer.cc`;
   * `game/lib.sh` and `game/smoke.sh`: the skeleton. `buildmap_golden.sh`, `render_regions.sh`, `resize_cycle.sh` and `regen_goldens.sh` stay with WP-07.
3. **`SHAPES_OBJS` does not get `shapes/pngio.o` yet** (§6.1's last sentence). The engine does not reference pngio today; only Exult Studio and the tools do. WP-08 adds it, together with the `hires_*` objects, when the engine's loader needs it. `HIRES_UNIT_OBJS` already contains `pngio.o`.
4. **`HIRES_PRESENT_OBJS` is empty**: `world_present.o` comes with WP-05.
5. **pytest runs in every `ci.sh` run**, not only with `U7_BG_STATIC` (§6.6). It is cheap, and data-dependent tests skip themselves; the art branch's real-data test does so too.
6. **`requirements.txt` is byte-identical to the one on `hires-art`** (blob `bde51f33`), so a later merge of the two branches gets no add/add conflict. It contains the three pins §6.1 asks for, plus that branch's comment about the GPU route-2 venv. The packages were already installed (the art track installed pytest 9.1.1 at 19:43).
7. **Test sources are not added to `Exult.vcxproj` or the Xcode project.** They are separate programs; on Windows, `Makefile.mingw` builds them through `Makefile.common`. They are allowlisted as `tests/**` with that reason. ExultStudio's and the tools' lists have no test entries either.
8. `EXULT_WRAPPER` is an environment variable of the game scripts (§6.5), not an `AC_ARG_VAR`. Only `TEST_WRAPPER` is configure-time, as §6.1 says. Since the review, `lib.sh` fills an empty `EXULT_WRAPPER` with §6.5's wrapper when exult is an ASan build, so the default is safe without a configure-time variable.
9. `check_build_lists.py` refinements:
   * generated files are excluded (rule targets, `BUILT_SOURCES`, git-ignored), and so are absent files. Otherwise the result depended on the build state; pure upstream's `.gitignore` lacks `data/shortcutbar_vga.h`;
   * Xcode paths are resolved exactly;
   * `--strict` and `--list-missing` were added;
   * the companion rule (review fix, §6) extends the lint to the lists §6.6 does not name: `Makefile.mingw`, every vcxproj under `msvcstuff` (Exult Studio and the tools) and each Xcode target, for the files that must follow another one.
