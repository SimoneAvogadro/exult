## 4. Presenter semantics (`probe_idx8 check`)

Setup:
* a 1920x1200 world drawn into a 1:1 window;
* the world is made of 6x6 blocks of random indices covering all 256 values, plus a 1-px checker (index ^ 1) that imitates dithered 6x art;
* the palette has distinct RGB values per index;
* as in Exult, the INDEX8 surface owns the palette (`SDL_CreateSurfacePalette`), and the texture shares it through `SDL_SetTexturePalette(t, SDL_GetSurfacePalette(s))`.

All six configurations (`direct3d11`, `direct3d12`, `vulkan`, `opengl`, gpu/D3D12, gpu/Vulkan) gave identical
results:

| # | Check (design reference) | Result |
|---|---|---|
| 1 | INDEX8 NEAREST 1:1 → backbuffer | exact |
| 2 | Resolve: INDEX8 NEAREST 1:1 → ARGB8888 TARGET texture, read back from the target (§3.2.4 "resolve before filtering") | exact |
| 3 | Resolved target → backbuffer, 1:1 NEAREST | exact |
| 4 | Palette tick without an upload: rotate 0xE0-0xE7 and 0xF8-0xFE and change entry 0x10 through `SDL_SetPaletteColors` on the **surface** palette, then draw → backbuffer, and → resolve target | both exact |
| 5 | Tracked rect upload: a 288x384 rect at (101,53), uploaded from the surface pointer and pitch, as `show_world_scaled` will do | exact |
| 6 | Palette alpha 0 on every entry, blend NONE (D-26): resolve; resolved → backbuffer; INDEX8 → backbuffer | all exact |
| – | *Control:* alpha 0 with SDL's default blend mode BLEND | every pixel wrong (the clear colour shows through). The explicit blend NONE is required, as D-26 says |
| 7a | LINEAR at r = 2/3 (1920x1200 → 1280x800): resolved path vs a CPU bilinear reference (texel centres, clamp) | max 1 LSB (54 of 1,024,000 px differ by 1), bias 0.000 |
| 7b | ARGB path (CPU LUT texture, LINEAR) vs the same reference | the same numbers. Resolved == ARGB exactly (0 px differ) |
| 7c | INDEX8 sampled LINEAR directly (palette-aware LINEAR; the design does not use it) | max 1 LSB vs the reference. It differs from the resolved path in 1 px (0 on `opengl`) |
| 8a | One 2:1 LINEAR pass into a TARGET (one halving step) vs the 2x2 box, .5 rounded up | max 1 LSB, but 575,900 of 576,000 px differ (bias −0.96) |
| 8b | The same pass vs the 2x2 box with .5 ties rounded down | max 1 LSB, 63,433 px differ, bias +0.04 |
| 8c | Two passes (r = 0.25) vs cascaded boxes, ties rounded up | **max 2 LSB** (14,722 of 144,000 px are off by more than 1), bias −1.07 |
| 8d | Two passes vs cascaded boxes, ties rounded down | max 1 LSB |
| 9 | PIXELART at 1:1 (resolved texture) | exact |

**What a 2:1 LINEAR pass computes.** A 16x4 experiment (`probe_idx8 <r> halvexp`) on D3D11 gave:
* uniform 100 → 100;
* columns 0/255 → 127;
* columns 100/101 → 100;
* averages that are not ties come out exact.

So the GPU rounds exact .5 averages down. SDL's software renderer does the same (bias −1.00 in 8a). In this test
world every aligned 2x2 block lies inside one dither pair, so almost every average is a tie. The consequence for the
halving-chain test is in §7, W2-3.

## 5. Timings

### 5.1 Upload cost (`bench_win`, "upd" in ms; ranges over the 3 filters and both passes)

| Renderer | INDEX8 full, 1920x1200 (2.3 MB) | INDEX8 full, 5160x1800 (9.3 MB) | INDEX8 rect 288x384 | ARGB LUT + upload, 1920x1200 | ARGB LUT + upload, 5160x1800 |
|---|---|---|---|---|---|
| `direct3d11` | **0.14-0.17** | **0.42-0.43** | 0.03-0.08 | 0.43-1.06 | 1.55-3.24 |
| `direct3d12` | 0.54-1.00 | 1.51-2.71 | 0.25-0.31 | 1.96-4.27 | 9.11-11.86 |
| `vulkan` | 0.88-4.81 | 2.62-4.99 | 0.30-0.60 | 3.03-4.55 | 8.25-11.65 |
| `opengl` | 0.34-0.42 | 0.53-0.65 | 0.21-0.29 | 1.90-1.94 | 7.11-7.64 |
| `gpu` (Vulkan) | 0.18-0.20 | 0.52-0.54 | 0.07-0.09 | 0.87-0.94 | 3.81-3.94 |
| `gpu` (D3D12) | **342-449** | not run | 5.98-14.48 | 5.00-5.03 | > 2,900 (²) |

(²) From `probe_idx8` (T4): 40 frames did not finish within 120 s (§5.3).

* A palette change ("B palette only") uploads nothing. SDL syncs the palette at draw time, so its cost shows in the draw call: 0.03-0.07 ms on D3D11, about 0.22 ms on D3D12, 0.29-0.60 ms on Vulkan and 0.07 ms on gpu/Vulkan. On OpenGL it moves into the present.
* The SDL `direct3d12` and `vulkan` renderers upload 3-10x more slowly than `direct3d11`, and their run-to-run spread is wide (`vulkan` INDEX8 full upload: 0.88-4.81 ms).

### 5.2 Presenter sequences (`probe_idx8 time`, total ms per frame, one pass)

Each sequence is what `show_world_scaled` will do per frame:
* **T1**: INDEX8 full upload, resolve into the ARGB target, LINEAR draw, present;
* **T2**: palette tick only, then T1 without the upload;
* **T3**: as T1, but with a 288x384 rect upload;
* **T4**: ARGB, full CPU LUT conversion and upload, LINEAR draw;
* **T5**: INDEX8 full upload drawn directly with NEAREST (the 1:1 path);
* **T6**: ARGB 288x384 rect, LUT conversion and upload.

| Renderer | 1:1, 1920x1200: INDEX8 (T5) | 1:1: ARGB (T4) | 1920x1200 → 1280x800: INDEX8 (T1) | → 1280x800: ARGB (T4) | 5160x1800 → 3440x1440: INDEX8 (T1) | → 3440x1440: ARGB (T4) | 5160: palette tick (T2) | 5160: INDEX8 rect (T3) | 5160: ARGB rect (T6) |
|---|---|---|---|---|---|---|---|---|---|
| `direct3d11` | **0.23** | 0.82 | **0.24** | 0.99 | **0.61** | 3.04 | 0.28 | 0.28 | 0.25 |
| `direct3d12` | 1.96 | 5.37 | 1.24 | 3.75 | 4.87 | 16.25 | 0.67 | 0.76 | 0.80 |
| `vulkan` | 1.59 | 4.61 | 2.65 | 7.02 | 6.12 | 13.24 | 0.82 | 0.81 | 1.89 |
| `opengl` | 0.37 | 2.36 | 0.39 | 2.32 | 0.60 | 8.67 | 0.24 | 0.30 | 0.30 |
| `gpu` (Vulkan) | 0.46 | 1.83 | 0.38 | 1.58 | 0.86 | 5.98 | 0.38 | 0.38 | 0.35 |
| `gpu` (D3D12) | – | – | (T3: 5.30) | 5.38 | – | > 2,900 | – | – | 20.96 (1920x1200 world) |

* **INDEX8 vs ARGB.** INDEX8 is 2.2-14x cheaper per full frame. On the 860x300 profile with `direct3d11`, the whole present path costs 0.61 ms per full-upload frame. With ARGB on `direct3d12` (16.25 ms) the present path alone would use up the 60 Hz frame budget.
* **The resolve pass** (T1) costs nothing measurable compared with `bench_win`'s direct INDEX8 LINEAR draw: for example 0.24 ms against 0.23-0.24 ms on D3D11 at 1280x800. The exception is `vulkan`, where the render-target switch costs 0.5-2 ms of CPU per frame (the "draw" column of T1-T3 in the log).

### 5.3 The `gpu` renderer on its D3D12 backend

* **Backend choice.** On Windows, SDL picks the D3D12 GPU backend for the `gpu` renderer. Its backend order is Metal, D3D12, Vulkan (`SDL_gpu.c:314-325`).
* **The code path.** Windows 10 19045 lacks `UnrestrictedBufferTextureCopyPitchSupported`. With `SDL_LOGGING=*=warn`, SDL logs "CheckFeatureSupport for UnrestrictedBufferTextureCopyPitchSupported failed. You may need to provide a vendored D3D12Core.dll through the Agility SDK on older platforms.". Every texture upload whose row pitch is not a multiple of 256 bytes therefore takes `SDL_gpu_d3d12.c:6045-6111`:
  * it creates a new upload buffer for each upload;
  * it fills that buffer row by row with `memcpy` **from the mapped transfer buffer**, which is upload-heap memory and very slow to read.
* **Measured, unaligned pitches:**
  * INDEX8 full upload at 1920x1200 (1920-byte rows): 342-449 ms per upload, in 3 runs;
  * INDEX8 288x384 rect: 5-15 ms;
  * ARGB 288x384 rect (1152-byte rows): 20 ms;
  * ARGB full upload at 5160x1800 (20,640-byte rows): more than 2.9 s.
* **Measured, aligned pitches:**
  * ARGB full upload at 1920x1200 (7,680 = 30·256 bytes): 3.9-5.0 ms;
  * **INDEX8 full upload at 2048x1200 (aligned): 0.73-0.78 ms.**

  So the pitch causes it, not the format.
* **Effect on Exult.** Exult's world texture widths, 320·6 = 1920 and 860·6 = 5160 bytes per INDEX8 row, are not multiples of 256, and tracked rects are unaligned in general. Both formats are therefore unusable on this configuration.
* **Who is affected.** Exult never chooses this configuration by itself. `SDL_CreateRenderer(window, nullptr)` (`imagewin.cc:626`) takes `direct3d11`, the first entry in SDL's list (`SDL_render.c:110-148`). It happens only when the user sets `SDL_RENDER_DRIVER=gpu`. With `SDL_GPU_DRIVER=vulkan`, the `gpu` renderer is fast and exact.

The deferred GPU area shader (D-19), recorded for reference only:
* DXIL runs correctly on D3D12 and SPIR-V on Vulkan: max 1.00 LSB at k = 1 and 0.68 LSB at k = 1.5;
* at 5160x1800 → 3440x1440 (k = 1.5 × 1.25) the error is 1.21 LSB.

## 6. Recommendation: `present_format` on Windows

1. **`present_format=auto` → INDEX8 on every Windows renderer.**
   * WP-15 rule 3 needs exact read-back per renderer, and it is exact on all of them, so no per-renderer ARGB exception is needed.
   * WP-14's runtime fallback stays as designed: the format list lacks INDEX8, or creating the texture or setting the palette fails. It did not trigger anywhere here, because INDEX8 creation and `SDL_SetTexturePalette` succeeded on all six configurations.
   * `present_format=argb` stays as the A/B switch and as the SDL 3.2 baseline.
2. **Why INDEX8, beyond exactness:**
   * it is 2.2-14x cheaper per full frame (§5.2);
   * a palette tick uploads nothing: 0.24-0.82 ms per frame in total at the 860x300 size, against a full ARGB conversion of 0.8-16 ms. That is what makes the 100 ms `rotatecolours` present at S>1 (§3.2.5) cheap.
3. **Renderer: keep SDL's default, `direct3d11`.** It is the fastest on every measure:
   * with INDEX8, 0.23 ms per full 1:1 frame at 1920x1200 and 0.61 ms on the 860x300 profile;
   * `direct3d12` and `vulkan` cost 5-10x more: 1.2-6.1 ms per full INDEX8 frame, and 13-16 ms with ARGB on the 860x300 profile;
   * WP-15 rule 1 measures the best of D3D11 and D3D12, which will be D3D11.

   No renderer configuration key is needed.
4. **The `gpu` renderer** should be documented as unsupported on Windows unless `SDL_GPU_DRIVER=vulkan` is set (WP-18 user guide). WP-14 may log one warning when `SDL_GetRendererName()` is `gpu` and `SDL_GetGPUDeviceDriver(SDL_GetGPURendererDevice(r))` is `direct3d12`. A code mitigation exists if it is ever needed: pad the INDEX8 texture width to a multiple of 256 px and widen tracked uploads to whole rows. The aligned full upload measured 0.73-0.78 ms. It is not worth the code while the default renderer is unaffected.
5. **Keep the resolve pass** of §3.2.4.
   * On this hardware it is not needed for correctness: INDEX8 sampled LINEAR directly matches the resolved path within 1 LSB, in 1 px.
   * But it costs nothing measurable except on `vulkan` (about 1 ms of CPU for the target switch).
   * It keeps the INDEX8 output identical to the ARGB output (0 px differ).
6. **PIXELART.** It is exact at 1:1 on all shader renderers. Fractional PIXELART was not compared with a reference, for lack of a reference implementation. WP-15 checks it visually (§3.2.4).

## 8. Deviations from the task text

* **Extra sizes.** Configurations were added: 1:1, because the listed command does not run the INDEX8 check, and 5160x1800 → 3440x1440, the user's profile, as proposal B's WP2 also planned.
* **Supplementary probe.** `probe_idx8` was added for the reasons in §1. It is not part of the repository: it lives in `tmp/wp02/`, next to its logs, like `bench_win.c` in `tmp/b_perf_gpu/`.
  * The probe was refined during the step: first a bias column, then the tie-down references, then T6 and a test mask.
  * The `p_*_check` and `t_*` runs used the third version.
  * The final binary (SHA-256 `c1ce7361…36f8e8d6`) only adds T6 and the mask. It reproduced the D3D11 check results (`p_direct3d11_check_final`).
* **gpu/D3D12 runs.** `timeout 120` killed the gpu/D3D12 `bench_win` runs after their checks and the first timing block. The cause was diagnosed with the 2048-wide experiment instead of longer runs.
* **`opengl`** was added because it is in the WP-15 matrix (§7.2 step 7). It ran one pass.
* **JSON.** `bench_win` prints text only. The "probe JSON" of §6.7 is therefore `WP-02_probe.json`, which `collect.py` writes from the logs. The probe runs carry their own JSON line.
