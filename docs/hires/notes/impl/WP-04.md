### 1.1 Primitive by primitive (all in `ibuf8_scaled.cc`)

Logical API, physical storage (I1): `bits` is the physical address of logical (0, 0), `line_width` the physical
pitch, logical (x, y) is the S x S block at `bits + y*S*line_width + x*S`. Every `s_*` clips in logical
coordinates with the existing helpers of `imagebuf.h` (`clip`, `clip_x`), reports the clipped logical rectangle
to the tracker, then writes the physical blocks.

| Primitive | Scaled body |
|---|---|
| `fill8(pix)` | `S*height` physical rows of `S*width` bytes from the storage origin; tracker = whole logical extent |
| `fill8(rect)`, `fill_hline8` | logical clip, memset `S*w` bytes on `S*h` (resp. `S`) rows |
| `copy8`, `copy_hline8` | logical clip, `rep_row` (each byte x S, specialised for S = 2, 3, 6) + `dup_rows` |
| `copy_hline_translucent8` | opaque source pixel: S x S block; translucent: `xforms[c - first][*p]` on **every** physical pixel |
| `fill_hline_translucent8`, `fill_translucent8` | `xform[*p]` on every physical pixel of the clipped span |
| `copy_transparent8` | non-zero source pixels become S x S blocks |
| `get_pixel8` / `put_pixel8` | top-left physical sample / logical clip, then a block |
| `draw_line8` | upstream's clip (`clipline`, the shrunk clip, the corner test) and its 16:16 walk in game px, each pixel plotted with `s_fill8(..., 1, 1)` or `s_fill_translucent8(..., 1, 1)`: S px thick lines (§1.4) |
| `copy` | **clipped**: source and destination intervals are both cut to the logical extent per axis (64-bit arithmetic, so huge rects cannot overflow), each cut shifting the other; then `memmove` of `S*h` physical rows (bottom-up when moving down) |
| `fill_static` | one `std::rand() % 5` per **logical** pixel, row by row as at S=1, then a block: RNG consumption equals S=1 |
| `paint_rle`, `paint_rle_remapped` | one shared `s_paint_rle(xoff, yoff, data, trans)`: each on-screen scan is decoded (remap applied) into a process-wide heap row buffer grown to `scanlen`, then drawn with `s_copy_hline8`, which clips. Raw unremapped scans pass the input pointer directly. Each run is clamped to `min(count, scanlen - b)` while the input still advances by the full encoded size (MS-5) |
| `create_another` | owned buffer of **the same scale** |
| `get` / `put` / `blit` | see §1.2 |
| `put_phys` (new) | physical copy clipped against `clip x S` and the source size `pw x ph`; tracker gets the logical bbox (floor for the start, ceiling for the end) |

### 1.2 Mixed scales (judge must-fix, MS-9)

* A physical row copy happens only between equal scales and always honours **both** buffers' `line_width`.
  Across scales each logical pixel is the top-left physical sample of the source, replicated to the
  destination scale (`copy_blocks`).
* `blit(src, x, y)` copies src's **storage extent** (logical `[-off_x, w - off_x) x [-off_y, h - off_y)`), so
  that src's logical (0, 0) lands on (x, y), clipped to this buffer's clip.
* `put(src, x, y)`: both scales 1 → upstream's `copy8(src->bits, w, h, ...)` unchanged; otherwise `blit`.
* `get(dest, x, y)`: both scales 1 → upstream body unchanged; otherwise dest's storage extent is filled so that
  dest's logical (0, 0) takes (x, y), clipped (as upstream) to this buffer's clip only. dest's tracker sees the
  write.
* A mixed call prints `[hires] mixed-scale <op>: scale A to scale B (sampled or replicated; logged once)`
  once per process for each `op` of "get", "put" and "blit" (`put` and `blit` share `s_blit`, which takes the
  operation name).

## 2. Deviations from the spec (the code is the truth)

1. **Tracker calls.** §3.1 puts `tracker->add()` inside the helpers `phys`/`rep_row`/`dup_rows`. Those helpers
   work on physical pointers and do not know the logical rectangle, so each `s_*` primitive calls
   `track(tracker, clipped logical rect)` once, right after its clip and before any write. `tracker_complete`
   (§4) proves that no write escapes it.
2. **Hook form.** `if (pixel_scale != 1) { return s_x(...); }` (a `return` of a void expression) instead of
   `{ s_x(...); return; }`: still one line, same effect.
3. **`fill8(pix)` and the pitch padding.** Upstream's S=1 body fills `line_width * height` bytes, i.e. also the
   padding at the end of every row of a padded layer. The S>1 body fills the storage only (`S*width` per row,
   as §3.1 says). The padding is never shown; the O1 test accounts for it (it refreshes the reference's
   canaries after `fill_all`).
4. **`put_phys` at S=1** is not hooked (it is new) and works at any scale, including 1.
5. **`blit` at S=1/S=1** (called directly) uses the storage extent and both pitches. Only `put` keeps upstream's
   behaviour at S=1/S=1 (I2): it reads the source with its *width* as the pitch and ignores its offsets.
6. **Views with "negative offsets".** The tests use view offsets of both signs: positive (the logical extent
   starts at a negative coordinate, the engine's main-buffer case) and negative (logical (0, 0) outside the
   storage; the test allocation leaves room so that `bits` stays inside it).
7. **Xcode project** registered as well (§9 calls it optional): `check_build_lists.py` requires it once
   `ibuf8_scaled.cc` exists.
8. `gamerend.cc:529` stays for WP-06 (see §1.3).

### 3.1 Findings while testing

Three first-run failures were all expectations of the test, not bugs of the code: (a) a miscounted Write_tracker
height in the test; (b) at S=1/S=1 `put`/`get` run upstream's code, which has no tracker (the engine sets a tracker
only on the scaled main buffer), so the tracker check applies there to `blit` only; (c) upstream's `fill8(pix)`
writes the pitch padding of a padded view (deviation 3), so the reference's canaries are refreshed after `fill_all`.

### 3.2 Verifier mutations (`tmp/wp04v_mut`, build-o2, `-tc='ibuf*'`)

m0 (identity) passes; m1 (tracker of fill), m2 (translucency on one row only), m4 (`put_phys` floor),
m5 (`blit` ignoring offsets), m6 (`fill_static` per physical pixel), m7 (`copy` direction), m8 (`get` tracker),
m9 (`create_another` scale), m10 (`get_pixel8`) are all caught. **m3 (RLE run clamp removed) is not caught**,
not even under ASan (m3_asan): the row buffer is process-wide and already grown to 32,767 bytes by earlier
cases, so an overshooting run writes inside its capacity and only `scanlen` bytes are drawn. The clamp is a
defence that no current test can observe (see §8).

## 8. Known limitations

* Nothing in the engine uses a scale other than 1 yet: the main buffer becomes scaled in WP-05 (§6), so the
  game still runs exactly the upstream path (buildmap goldens equal).
* The RLE run clamp of `s_paint_rle` (MS-5) is untested in effect (§3.2, m3): a test would need a fresh,
  exactly sized row buffer (e.g. a test-only hook to shrink it) to make an overshoot visible to ASan.
* The scaled bodies are byte loops (`fill_blocks`, `xform_blocks`, the RLE decode); performance work is WP-16.
* `put`/`get` at S=1/S=1 keep upstream's contract (source width as pitch, offsets ignored); only `blit()` honours
  the storage extent and both pitches at S=1.
* `gamerend.cc:529` still `copy8`s the 1x flats cache (correct NN at S>1); WP-06 makes it a `blit`.
