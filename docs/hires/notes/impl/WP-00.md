* The logs are in `deps/src/build-sdl32-{cmake,build,install}.log`. The flags follow the 3.4.18 build (`deps/src/build-sdl3/CMakeCache.txt`).
* `SDL_X11_XTEST` does not exist in 3.2. cmake warns that it is unused, which is harmless.
* The feature set matches 3.4.18's where it matters: X11, dummy and offscreen video, PulseAudio, and the GLES2, Vulkan and GPU renderers.
* Desktop OpenGL is off in **both** builds, because the sysroot has no GL headers.
* The cmake summary prints `SDL_INSTALL (Wanted: ON): OFF`. That is a display quirk of the 3.2 summary: the cache has `SDL_INSTALL=ON` and the install works.
* Provenance (round 3). Rounds 1 and 2 did not check the signature: the key was not in a keyring, and the SHA-256 above was computed locally, with no independent value to compare it with. Round 3 ran the check above with throwaway keyrings in `tmp/wp00/fix3/gnupg*`:
  * `gpg --verify` reports `Good signature from "Sam Lantinga <slouken@libsdl.org>"`, made 2025-05-14 20:02:33 CEST with DSA key `1528 635D 8053 A57F 77D1 E086 30A5 9377 A776 3BE6` (dsa1024, created 2001-01-05). gpg also warns that the key is "not certified with a trusted signature", which is expected in a fresh keyring.
  * The key anchor does not depend on the keyserver alone. The key block that https://www.libsdl.org/signing-keys.php publishes contains the same key, together with a newer RSA key (`0900 1043 … 4B61 D39B`), and verifying against that import gives the same Good signature.
  * The reviewer had already verified it the same way from the keyserver.
  * The tarball has 15,888,107 bytes and SHA-256 `b7e7dc05…9c1f`, the values recorded in rounds 1 and 2.

**Build-time resolution.** pkg-config's built-in search path is `deps/prefix/lib/pkgconfig:deps/prefix/share/pkgconfig`, so 3.4.18's `sdl3.pc` is always found last:
* `PKG_CONFIG_PATH=/nonexistent pkg-config --modversion sdl3` prints `3.4.18`.
* Leaving 3.4.18's directory out of `PKG_CONFIG_PATH` therefore excludes nothing. Round 1's lane got 3.2.14 only because `prefix-3.2` is searched first. If `prefix-3.2/lib/pkgconfig/sdl3.pc` were missing (for example in `ci.sh` before the SDL step), the lane would have built against 3.4.18 without any error.
* `PKG_CONFIG_LIBDIR` set to the sysroot dirs replaces the built-in path. With it, a missing `prefix-3.2` makes configure fail. Round 2 checked this with a non-existent prefix: configure stops at `checking for sdl3... no` with `*** SDL not found!`. `configure_all.sh` also asserts the version and the Makefile's `SDL_CFLAGS`.
* `PKG_CONFIG_PATH` with **only** `prefix-3.2`, as in DESIGN.md revision 2, makes configure stop with "must have Ogg/Vorbis installed". libpng, zlib, ogg, vorbis and alsa are found only through the sysroot dirs.

**Run-time binding.** The problem has three parts:
* SDL's `sdl3.pc` links with `-Wl,--enable-new-dtags`, which produces DT_RUNPATH.
* `env.sh` puts `deps/prefix/lib` (3.4.18, same soname `libSDL3.so.0`) into `LD_LIBRARY_PATH`.
* `LD_LIBRARY_PATH` takes precedence over RUNPATH.

So a plain `build-sdl32` binary would silently run against 3.4.18 whenever `env.sh` is sourced. The fix is
`LIBS="-Wl,--disable-new-dtags"`. LIBS comes last on the link line, so it overrides the `.pc` flag and
the rpath becomes DT_RPATH, which the loader searches **before** `LD_LIBRARY_PATH`.

Checked with `env.sh` sourced (round 2, after the reconfigure and relink):
* `readelf -d build-sdl32/exult` shows `RPATH [.../deps/prefix-3.2/lib:...]`.
* `ldd build-sdl32/exult` resolves to `deps/prefix-3.2/lib/libSDL3.so.0`.
* `LD_DEBUG=libs build-sdl32/exult --version` prints `calling init: .../prefix-3.2/lib/libSDL3.so.0`.

WP-01's `hires_unit` and `hires_present` link with the same `LIBS`, so they inherit the fix.

**Finding 2: buildmap output depends on heap address order, and therefore on the harness.**
* The cause: `Game_object::dependencies` is a `std::set<Game_object*>` (`objs/objs.h:93-98`), and `Game_render::paint_object` (`gamerend.cc:592-615`) paints an object's dependencies in set order, which is **pointer order**.
* The effect: where the dependency graph is ambiguous or cyclic (the `render_seq` guard), the paint order of overlapping objects follows the heap addresses.
* The evidence:

## 5. ASan lane: the g++ 9.4 stall and fatal UBSan

**Problem.** DESIGN.md revision 2's flags (`-fsanitize=address,undefined`) never finished `exult.cc`:
`cc1plus` ran for 38 min at 100 % CPU before it was stopped.

**Cause.** configure's warning set includes `-Wduplicated-branches`. g++ 9.4 stalls on that warning in
UBSan-instrumented code: the `null`, `alignment` and `vptr` checks add the C++ front end's
`this`/reference instrumentation, and `-Q` puts the stall in the front end, inside `main()`. Disabling
the 54-line `cerr << … << endl` usage chain (`exult.cc:330-383`) also avoids it. Measured on

Round 1's bisection removed the three checks, because each of them alone stalled while the warning was

**Fix (round 2).** `build-asan`'s CXXFLAGS get `-Wno-duplicated-branches`, and **every UBSan check is
back on**, including `null`, `alignment` and `vptr`. The other lanes still compile with the warning, so
no diagnostic is lost overall. The full ASan build took 511 s at -j6 (round 1, without the three checks: 364 s at -j8).

**Fatal UBSan.** g++ 9's UBSan is recoverable by default. It prints `runtime error:` and carries on, so
`make check` and the game scripts would pass with UB reports. The lane therefore compiles with
`-fno-sanitize-recover=undefined`, and the wrappers add
`UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`. `tmp/wp00/buildmap_golden.sh` now fails when the
log contains `runtime error:` or a sanitizer report, whatever the exit code. This was tested with a fake
`exult` (`tmp/wp00/fix2/fakebuild/exult`) that writes 144 dummy PNGs, exits 0 and prints one report line.
The script fails (rc=1) on `runtime error:`, `ERROR: AddressSanitizer`, `SUMMARY:
UndefinedBehaviorSanitizer` and `AddressSanitizer:DEADLYSIGNAL`, and passes when no line is printed.
The check for fatal UBSan is
`tmp/wp00/ubsan_fatal.sh`. It compiles the reviewer's `ub.cc` (copied as `tmp/wp00/ubsan_probe.cc`:
signed overflow, then an oversized shift) with the lane's own CXXFLAGS and LDFLAGS, and runs it under
the lane's `TEST_WRAPPER`. Result: it exits with rc=1 after exactly one report, with a stack trace. The
control build, without `-fno-sanitize-recover` and run without `halt_on_error`, reports both errors and
exits 0. The `exult` binary links only the `_abort` variants of the UBSan handlers, including
`dynamic_type_cache_miss` (vptr) and `type_mismatch_v1` (null, alignment). The one exception is
`builtin_unreachable`, which is always fatal.

**Leaks and ASLR during the build.** configure runs ASan test programs, and the data build runs ASan
tools (expack, ucc, the data generators). So configure, make and make check run with
`ASAN_OPTIONS=detect_leaks=0` under `setarch x86_64 -R timeout`: tool leaks at exit would fail the build,
and ASLR makes ASan hang (§6.5). Test programs get `detect_leaks=1` from `TEST_WRAPPER`. With these
flags, configure gives a `config.h` identical to `build-o2`'s.

## 7. Deviations and notes

* `make -j6` instead of §7.1's `-j16`, with one tree at a time. This machine's RAM is unstable under heavy load: bit flips were measured, and the PC has gone down twice, once in the middle of round 2's first attempt (which left `build-asan` with five empty files). `build_all.sh` retries a failed make once and reports both results, and a failure that does not reproduce counts as a suspected hardware fault. Round 1 saw two such one-off failures, both in libtool's hidden non-PIC compile (`imagewin/scale_hq4x.lo`, `shapes/shapevga.lo`). Both compiled on the immediate retry, and there was no OOM event.
* The verifier suggested `LIBTOOLFLAGS=--no-suppress` to show the hidden compile's output. It does not work: libtool 2.4.7 rejects `--no-suppress` as a global option ("unrecognised option"), because `-no-suppress` is a compile-mode argument, and automake puts `LIBTOOLFLAGS` before `--mode=compile`. It is not used.
* `build-asan`: `-fno-sanitize-recover=undefined -Wno-duplicated-branches`, and configure, make and make check under `setarch -R` with a timeout (§5). These are now in the spec (revision 2.1).
* `build-sdl32`: `PKG_CONFIG_LIBDIR` and `LIBS="-Wl,--disable-new-dtags"` (§2.2), now in the spec.
* Every configure call passes the pkg-config variables as arguments, so a recheck reuses them. `env.sh` is still required.
* `exult-upstream` is a detached worktree, as in §7.1's command. Suggestion for WP-03: run `git -C exult-upstream switch -c upstream-ref` before the P3 cherry-pick, so the commit sits on a named branch.
* Extra goldens for `--buildmap 0` and `1`. They were not required, but they are cheap and O0 uses all three levels.
* Findings 1 and 2 (§3) affect how WP-03 and WP-07 read the goldens.
* Seen but not touched: another track created the worktree `exult-hires-art` on branch `hires-art` (also at `8b6ab6b43`) while WP-00 ran.
* Shared source tree: the data build writes generated files into the **source** tree (`exult-hires/data/*.flx`, `*_flx.h`, `*_vga.h` and so on; all ignored). Building two lanes **at the same time** races on those files, and building one lane can force about 20 recompiles in the others (§6).
