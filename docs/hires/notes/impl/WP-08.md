## 2. PNG reader and writer (`hires_png`, D-11, MS-7)

`read_indexed_png(path | bytes, expect_w, expect_h, Indexed_png&)`:
1. The file is opened once (`std::ifstream` on a `std::filesystem::path`, no `FILE*` across a DLL boundary) and its
   first 33 bytes (signature and IHDR) are read and checked first (size, colour type), so a stray image of the
   wrong size or type is rejected (F3, F1) without being read whole (second fix round, §14). Its size is checked
   against a cap (twice the raw image plus 64 MiB for metadata; review fix, it was 1 MiB); a larger file with a good
   head is F1 "file too large".
2. The chunk structure is scanned in memory the way `hirescheck.py`'s parser reads it: signature, every chunk
   complete up to IEND, CRC of every critical chunk (an ancillary chunk with a bad CRC is skipped), IHDR first and
   13 bytes, PLTE length a multiple of 3 in 3..768. Failures are `read_error` (rule F1, "unreadable PNG").
3. Size, then colour type, in `hirescheck.py`'s order: `wrong_size` (F3), `not_palette` (F1). This happens **before
   libpng is called and before any pixel buffer exists**, so a 30000x30000 IHDR costs one small file read.
4. libpng gets only the chunks the reader uses: the critical ones, tRNS and the text chunks up to 1 MiB (review fix).
   Every other ancillary chunk (ICC profile, EXIF, XMP, physical size, private chunks, oversized text) is dropped
   from a copy of the buffer after the structure scan has checked it, so editor metadata can neither hit libpng's
   1 MiB chunk limit ("chunk data is too large", a hard error) nor make a file F1 that `hirescheck.py` accepts.
   When nothing is dropped (mkpack's tiles) the buffer is used as it is.
5. libpng decodes from memory inside one function whose post-`setjmp` locals are POD; every heap buffer (pixels, row
   table, writer output, text records) belongs to objects constructed before `setjmp`, and the libpng structs are
   freed by the destructor of the frame object on every return path. The allocator callbacks never throw (an
   exception must not cross libpng's C frames); libpng's errors `longjmp` back with their message in a POD buffer,
   and the caller turns it into `error` (nothing is built in the `setjmp` branch: that silenced the ASan lane's
   `-Wclobbered` false positive). Defence in depth: `png_set_user_limits(expect_w, expect_h)` (stricter than §3.5's
   `128·S_art`) and `png_set_chunk_malloc_max(1 MiB)`; benign errors are warnings.
6. Depths 1/2/4 are expanded with `png_set_packing`; Adam7 is handled; indices stay raw (no rotation, no lookup).
   The PLTE, the presence of tRNS (from the scan, as the Python parser sees it) and every tEXt/zTXt/iTXt up to 1 MiB
   from before and after IDAT (libpng's `info` and `end_info`) are returned in file order; `find_text` returns the
   first match, like `hirescheck.py`'s `setdefault`.

Allocation statistics (`png_alloc_stats`, the "counting allocator hook" of §6.2) count libpng's allocations through
the reader's allocator plus the reader's own file and pixel buffers.

`encode_indexed_png` / `write_indexed_png` write palette PNGs (depth 1/2/4/8, optional tRNS, tEXt before and after
IDAT, optional Adam7) under the same `setjmp` rules, deterministically (no tIME, filter none, zlib level 9). WP-11
(`--dump-art`) can use it for templates with guards.

Without libpng (`HAVE_PNG_H` undefined: iOS, Android) every read returns `no_png_support`; loose PNGs are then
rejected as F1, and bundles still work because they need no PNG decoder. All new files compile without warnings in
that configuration (checked with a copy of `config.h` without `HAVE_PNG_H`).

## 3. The store (`hires_store`)

`Store::load(roots, scale, s_art, pal, provider)` never throws, and it fails at the smallest unit (I11, review fix):
an exception (`std::bad_alloc`, I/O, the provider) while one file or bundle entry is checked or reduced rejects that
file or entry alone (severity `error`, detail `cannot check: …`; in a group the group is skipped, "… could not be
checked"); one while the bundle is read disables the bundle (B0, `cannot read: …`); anything else disables its root
(`root-disabled`, `load failed: …`), whose results are merged only at its end (all or nothing). Only a failure of
the final commit leaves the store empty with an `error` finding. Paths in findings and `Entry_info` are UTF-8 in
the generic format (`/` separators on Windows too), and a name without a UTF-8 form is shown with `?` instead of
throwing. Per root, in precedence order:
1. **R1.** If `pack.txt` exists, its `palette_crc32` (1-8 hex digits, optional `0x`/`0X`, blanks and a UTF-8 BOM
   ignored) must equal `palette_crc32(pal)`; otherwise (or if unreadable or malformed) the root is disabled with one
   `root-disabled` finding. The engine reads no other key.
2. **Folder.** `x<S>` if it exists; else, when `S < S_art` and `S_art % S == 0`, `x<S_art>` with reduction (§5.6);
   else nothing from this root (an `info` finding).
3. **Bundle** `flats.bundle`: B0 checks (§4), then each entry independently, in file order (which need not be
   sorted): N1 (frame < 32, the provider has a flat), P0, P4, G1 (when flagged). No group effect. Of two entries with
   one key the later accepted one wins, silently, as `hirescheck.py` counts them (review fix: the order and
   duplicate checks that disabled the whole bundle are gone).
4. **Loose** `flats/`: the top-level PNGs, then each group directory (directories `_*` and `.*` ignored, `*.off`
   disabled with an `info` finding), files in name order, non-recursive. Every `*.png` file is a candidate, hidden
   ones too (review fix, as `hirescheck.py`): a macOS `._0019_00.png` is an N1 reject and skips its group. Per file
   the rules run in `hirescheck.py`'s order N1, F3, F1, F2, F4 (warning), P0, P4, G1, and the first reject decides.
   A reject inside a group skips the whole group (G2, every member counted as rejected, one `group-skipped` finding
   naming the first failing file and rule). A key seen twice among accepted loose files: the later one wins with an
   N1 warning (hirescheck.py does the same).
5. A loose file beats the bundle entry of its root; the first root with an accepted candidate serves the key; a key
   rejected in a higher root falls back to a lower root's candidate.
6. Accepted x6 art is validated **before** reduction (G1 and P4 on the x6 data) and reduced with `reduce_mode` using
   the live 1x flat as the parent.
7. `terrain/`: names `<16 lowercase hex>.png` are indexed (another `.png` name is an N1 reject); first root wins.

The served tiles live in one arena in key order; `flat(shape, frame)` uses `frame & 31` and returns
`{px, side = 8·S}` (MS-6). `explain_flat` / `explain_terrain` return the served candidate or else the
highest-precedence rejection (state, path, rule, detail, bundle/guard/reduced flags, root index).

`Store::terrain(key, layer1x, dst, w, h, pitch)` decodes on demand: it returns false and leaves `dst` untouched
unless `w == h == 128·S`, `pitch >= w`, `layer1x` is given and the file passes N1, F3, F1, F2, F4, P0, P4 (against
the terrain's 128x128 1x layer) and, when present, `Exult-Terrain-Key` equals the file name (else G1). Rejects are
latched and reported once through `take_findings()`; **P4 rejects are not latched**, because two terrains with the
same T1 key can have different layers (the fill under RLE cells; §5.2 known limitation). Exceptions (e.g.
`bad_alloc`) are caught and reported; nothing propagates into paint.

`Store_set` (engine-free, so it is unit-tested) holds one `Store` per scale, loaded on the first `flat`/`terrain`/
`store` call for that scale through an inputs function, with these rules: scale < 2 never loads; a failed load (an
exception from the inputs or the load) is latched until `invalidate()`; an exception from the report or text
function only loses that message (review fix), so `store`, `flat` and `terrain` never throw into paint;
`generation()` changes on `invalidate()` and on a real change of `set_enabled()`, never on a lazy load. The glue owns
one static `Store_set`.

`Rule` enumerators are lower case with their ID as prefix (`n1_name`, `f1_colour`, `f2_plte`, `f3_size`, `f4_trns`,
`p0_border`, `p4_cycling`, `g1_guard`, `g2_group`, `r1_palette`, `b0_bundle`; review fix): `<termios.h>` defines the
macro `B0`, which broke any translation unit that included it before `hires_store.h`. `rule_name()` still prints the
IDs (`N1` … `B0`) used by the log, the fixtures and `hirescheck.py`.

## 4. The bundle format (TB-2, D-12)

Written by `tools/hires/u7hires/pack.py` (`write_bundle`, hires-art) and read here, little-endian:

```
header, 16 bytes:  "U7HB" | u16 version = 1 | u16 scale | u32 palette_crc32 | u32 count
count entries:     u16 shape | u8 frame | u8 flags (bit 0: guard present) | u32 guard | (8·scale)^2 indices
file size == 16 + count · (8 + (8·scale)^2); entries written sorted by (shape, frame)
```

The reader checks, in pack.py's order and with its messages: size ≥ 16 (`truncated header`), magic, version, scale
== the folder's scale, palette CRC == R1's value, file size. These are exactly §5.5's B0 and pack.py's
`read_bundle()` checks; the entry order is not checked (review fix). It reads the 16-byte header first and the whole
file in one more read only when the size matches, so a bogus file is never read whole. Reserved flag bits are
ignored (as pack.py does). `build_bundle` sorts stably, like pack.py's `sorted()`. `tests/data/hires/bundle/` holds
a bundle and `pack.txt` written by pack.py itself.

## 10. Deviations from the spec

1. **The BG palette vector is not committed** (§5): only its CRC, checked by a game-data doctest. The task forbids
   EA-derived data in the repo; the clamp is covered by a synthetic vector.
2. **Rule order and IDs follow `hirescheck.py`** (hires-art), which the spec leaves open: N1, F3, F1, F2, F4, P0, P4,
   G1; unreadable files are F1 (not a separate ID); a malformed guard is G1; duplicates are an N1 warning with the
   later file winning.
3. **`Store::terrain` takes the terrain's 128x128 1x layer** (`layer1x`), which §5.5 needs for P4 and §5.6 for the
   reduction but §3.5's outline signature omits. Hence `Hires::terrain(key, S, layer1x, dst, w, h, pitch)`; WP-17
   adapts its `Image_buffer8` to the raw destination.
4. **`explain_at(tx, ty)` is not in the glue**: it needs `find_flat_source` (WP-03) and the T1 key cache (WP-17).
   WP-10 builds the inspector on `Hires::explain_flat` / `explain_terrain`, which are here.
5. **`Hires::reload(scale)`** reloads the current scale at once and returns its summary line (for WP-10's toast);
   `invalidate()` is the lazy variant.
6. **`Store_set`** (new, in `hires_store`): the per-scale stores, generation, toggle and fail latch live in an
   engine-free class so they are unit-tested; the glue only adds config, roots, palette, provider and logging.
7. **`reload_shapes` hook** only in the `U7_SHAPE_SHAPES` case (flats live only in `shapes.vga`).
8. **`shapes/pngio.o` is not added to `SHAPES_OBJS`**: the engine still does not use `Import_png8`/`Export_png8`
   (`hires_png` has its own reader and writer), so the object would only be linked unused.
9. **libpng user limits are the exact expected size** instead of `128·S_art` (stricter; the size is known).
10. **Only `hires_png` depends on libpng**: the rest of the store (bundles included) compiles and works without it.
11. Additions to the spec's API: `check_tile_file`, `check_tile_pixels`, `check_terrain_file` (shared by the store and
    the fixture tests), name/CRC helpers, `encode_indexed_png` with options, `build_bundle`, `Report::findings` (typed)
    next to `lines`, `Report::roots`/`roots_disabled`, `Severity::error` for engine failures.
12. **Report counts** `loaded`, `bundled` and `unguarded` describe the keys the store serves after precedence (the
    Python report counts per root).

**Behaviour the engine has and `hirescheck.py` (hires-art) does not yet** (recommended for WP-12 / the merge, so the
validator stays identical): a UTF-8 BOM in `pack.txt` is ignored; `palette_crc32` takes 1-8 hex digits; terrain
files are validated at decode with `Exult-Terrain-Key` mismatch = G1 and P4 rejects not latched; an unreadable
`pack.txt` disables the root. Resource limits of the engine alone, which no realistic file reaches: a tile or
terrain file larger than twice its raw image plus 64 MiB is judged on its IHDR (F3, or F1 "file too large"), and a
text chunk over 1 MiB is ignored (its key, if it were the guard, would not be seen). None of these changes a verdict
on the art track's packs (§9). The review removed three engine-only rules instead of porting them (§13): ignoring
hidden files, B0 for unsorted or duplicate bundle entries, and F1 for files over 1 MiB of metadata.
